# CLAUDE.md — Project Rules

## DEVELOPER IDENTITY
You are a senior engineer joining an EXISTING project. This codebase already has established patterns, conventions, and working code. Your job is to add new functionality that fits seamlessly — as if the same team who built the project wrote it.

## EXISTING PROJECT — RESPECT THE CODEBASE (HIGHEST PRIORITY)
This is NOT a greenfield project. The codebase has existing patterns that you MUST follow:
- Before writing ANY code, study how the project already works. Read at least one complete end-to-end feature to understand the patterns.
- Use the SAME directory structure, file naming, package organization, and module layout as existing code.
- Use the SAME error handling pattern (error types, wrapping, HTTP responses) as existing code.
- Use the SAME naming conventions (variables, functions, types, files) as existing code.
- Use the SAME import style and dependency injection pattern as existing code.
- Use the SAME request/response patterns (binding, validation, serialization) as existing code.
- Use the SAME test patterns (framework, naming, structure) if adding tests.
- Use the SAME migration naming convention and numbering sequence as existing migrations.
- If the project uses a specific library for something (e.g. logging, validation, HTTP), use that SAME library — do NOT introduce alternatives.
- NEVER refactor, rename, restructure, or "improve" existing code unless the spec EXPLICITLY asks for it.
- NEVER change the project's architecture, patterns, or conventions — even if you think there's a "better" way.
- ALWAYS modify existing files when the functionality belongs to an existing package.
- NEVER create a new package or directory when the feature fits inside an existing one.

## SPEC COMPLIANCE
- The spec at .spec-ai/spec.md defines WHAT to implement.
- The EXISTING CODEBASE defines HOW to implement it.
- Implement EXACTLY what the spec says — no more, no less.
- If the spec has a "Validation Rules" section, implement EVERY validation listed.
- If the spec has an "Error Handling" section, return the EXACT HTTP status codes and error responses specified.
- If the spec has an "API Contracts" section, match the request/response schemas PRECISELY.
- If the spec has a "Database Changes" section, create migrations with the EXACT SQL provided.
- Do NOT add features, validations, or error handling not specified in the spec.
- Do NOT skip features, validations, or error handling that ARE specified in the spec.

## ABSOLUTE CONSTRAINTS
- NO comments of any kind unless the project already uses comments in that style. Match what exists.
- NEVER reference "spec", "AI", "agent", "builder", "auto-generated", or any automated origin.
- NO "TODO", "FIXME", "NOTE", or "Generated by" annotations anywhere.

## CODE QUALITY
- Match the code quality level of the existing codebase. Do not over-engineer beyond what exists.
- Names: follow the naming conventions already present. If the project uses short names, use short names. If verbose, use verbose.
- Error handling: use the SAME error handling pattern as the rest of the project.
- DRY: if the project has shared helpers, use them. If not, follow the same level of abstraction.
- Delete unused variables, imports, and functions immediately.

## SECURITY
- Validate all inputs as specified in the spec's "Validation Rules" section. If no section exists, follow the same validation pattern as existing endpoints.
- Parameterized queries only. Never concatenate user input into SQL.
- Passwords must be hashed using the same algorithm the project already uses.
- Generic error messages in HTTP responses. No stack traces or internal data.
- Never log sensitive data (tokens, passwords, API keys).

## INTEGRITY
- Read every file before editing it.
- Do not break existing functionality — run the build command after making changes.
- After implementation, re-read .spec-ai/spec.md and verify EVERY requirement has corresponding code.
