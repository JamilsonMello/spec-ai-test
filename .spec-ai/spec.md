# Refatoração Global para Clean Code e Consolidação de Clean Architecture

# REFACTORING: Refatoração Global para Clean Code e Consolidação de Clean Architecture\n\n## Context and Motivation\nO projeto atualmente possui arquivos de documentação interna misturados ao código-fonte (como o `CLEAN_ARCHITECTURE_PLAN.md`) e utiliza nomenclaturas genéricas (ex: `u`, `r`, `err`) que dificultam a leitura rápida. Além disso, a presença de comentários redundantes em arquivos `.go` polui o ambiente de desenvolvimento. Esta refatoração consolidará os princípios de Clean Code e Clean Architecture, garantindo que o código seja autodocumentado e siga as convenções da linguagem Go, facilitando a escalabilidade e a entrada de novos desenvolvedores.\n\n## Out of Scope\n- Alteração de regras de negócio ou lógica de validação.\n- Mudanças em esquemas de banco de dados ou tabelas.\n- Criação de novas funcionalidades ou endpoints.\n- Alteração de dependências externas ou bibliotecas no `go.mod`.\n\n## Current vs Expected Behavior\n- **Atual:** Arquivos com variáveis como `u *User`, `r *http.Request`, `err error` e comentários explicando o óbvio.\n- **Esperado:** Variáveis com nomes contextuais como `user`, `request`, `internalError` e ausência de comentários em blocos de código onde o nome da função já expressa sua intenção.\n- **Atual:** Interfaces com nomes genéricos.\n- **Esperado:** Interfaces seguindo a convenção Go (ex: `UserRepository` ou `UserStorer`).\n\n## Functional Requirements\n- **FR-1:** Remover o arquivo `CLEAN_ARCHITECTURE_PLAN.md` da raiz do projeto.\n- **FR-2:** Remover todos os comentários de linha (`//`) e de bloco (`/* */`) de todos os arquivos com extensão `.go`.\n- **FR-3:** Renomear todas as variáveis de caractere único ou genéricas para nomes descritivos baseados no contexto (ex: em um handler de usuários, `u` torna-se `user`).\n- **FR-4:** Decompor funções que excedam 30 linhas em subfunções privadas com responsabilidade única.\n- **FR-5:** Padronizar nomes de arquivos para que reflitam exatamente sua responsabilidade (ex: `user_handler.go` em vez de apenas `handler.go`).\n\n## Key Entities\nAs entidades em `domain/entities/` devem manter seus campos, mas os métodos associados devem ter seus receivers renomeados de letras únicas para nomes representativos (ex: `func (u *User) GetName()` -> `func (user *User) GetName()`).\n\n## Validation Rules\n- Todos os DTOs em `application/dtos/` (ou pacotes equivalentes) devem seguir o padrão: `[Entity][Action]Input` e `[Entity][Action]Output`.\n\n## Error Handling\n- Renomear variáveis de erro de `err` para descrições específicas quando houver mais de um erro no escopo, como `dbError`, `validationError` ou `mappingError`.\n- Manter o retorno de erros conforme os padrões atuais do projeto, apenas melhorando a nomenclatura interna.\n\n## Files to Modify\n- `CLEAN_ARCHITECTURE_PLAN.md`: DELETE.\n- `**/*.go`: MODIFY - Remover todos os comentários, renomear variáveis locais, receivers e parâmetros.\n- `domain/interfaces/` (ou local de interfaces): MODIFY - Renomear interfaces para sufixos 'er' ou nomes de domínio claros (ex: `IUserRepository` -> `UserRepository`).\n- `application/usecases/`: MODIFY - Renomear arquivos e structs de DTO para o padrão Input/Output.\n- `infrastructure/repositories/`: MODIFY - Renomear métodos e variáveis internas para clareza.\n\n## Implementation Guidance\n1. **Remoção de Arquivos:** Excluir `CLEAN_ARCHITECTURE_PLAN.md`.\n2. **Limpeza de Comentários:** Varrer todos os arquivos `.go` e remover comentários não documentais (manter apenas comentários de exportação se exigido por linters, caso contrário, remover tudo).\n3. **Renomeação de Receivers:** Localizar `func (x *Type)` e alterar `x` para um nome descritivo em todo o projeto.\n4. **Refatoração de Handlers:** Identificar funções longas nos handlers e extrair lógica de parse/validação para funções auxiliares no mesmo arquivo.\n5. **Padronização de Interfaces:** Ajustar nomes de interfaces e atualizar todas as referências nos casos de uso e injeção de dependência.\n6. **Renomeação de DTOs:** Ajustar structs de entrada/saída para o padrão `Input`/`Output` e atualizar os casos de uso correspondentes.\n\n## Success Criteria\n- **SC-1:** O arquivo `CLEAN_ARCHITECTURE_PLAN.md` não existe mais na raiz.\n- **SC-2:** Nenhum arquivo `.go` contém comentários `//` ou `/* */`.\n- **SC-3:** Não existem variáveis de caractere único (u, r, e, i, j) exceto em contadores de loops extremamente simples.\n- **SC-4:** O projeto compila e executa todos os testes unitários com sucesso após as renomeações.\n- **SC-5:** Todas as interfaces seguem um padrão nominal consistente (ex: `UserRepository`).
